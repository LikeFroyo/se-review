# Fixture realism — input data that never occurs in production

Audit whether the inputs resemble what the system actually receives. A check proves only that
the code handles the data it was given, so unrealistic inputs make a suite report protection it
does not provide.

- **Stripped of the awkward members:** Optional fields, absent keys, empty collections, and malformed entries are removed from the fixture because they complicate the assertion — and are exactly what the code receives.
- **Uniform where production is irregular:** Consistent casing, whitespace, encoding, and ordering, on inputs that arrive with all four varying.
- **Only well-formed input:** A parser or validator is exercised exclusively on valid data, never on the invalid data it claims to reject, so the rejection path is untested.
- **One record reused everywhere:** A single happy-path sample is shared across many checks, so no second distinct input was ever required to pass.
- **Placeholder values that break their own constraints:** Identifiers, tokens, or addresses that violate the format, length, or range of the real thing, so validation never sees a realistic one.
- **No scale variation:** One or a handful of elements where production operates on many, hiding failure that only appears at size.
- **Timestamps that never cross a boundary:** Dates stay clear of period ends, leap days, and clock changes, so the boundary logic is never taken.
- **Fixture generated by the code under test:** The input is produced by the implementation, so the check cannot disagree with it by construction.
